# Kanan IELTS Portal: Full QA and Penetration Test Report

**Date:** 3 November 2026
**Build tested:** `main` at `92d2269`, plus three local regression fixes described in section 2
**Purpose:** find every bug, loophole and weakness before real papers and content are uploaded

---

## 1. Summary

The portal's core security is solid. Across 25 protected API routes tested against every role, there was no way to reach another person's data, bypass a role, defeat CSRF protection, or see an unreleased result. Contact details never reached a Trainer. Parallel requests never broke attempt limits or created duplicate results. Media and import validation rejected every hostile file I tried.

**The portal is not ready for real exams yet.** Two critical exam-integrity loopholes let a student defeat an FLT. Several high-severity issues will appear as soon as a full class uses it together:
- a timer that can be frozen indefinitely
- the whole paper being sent at the start
- logins failing when a class signs in at once
- test starts failing when everyone starts together
- account lockout by strangers
- unlimited paid AI calls

| Severity | Count | Meaning |
|---|---|---|
| Critical | 2 | Defeats an exam. Fix before any graded FLT. |
| High | 7 | Will hit real users or cost money. Fix before launch. |
| Medium | 9 | Wrong behaviour, errors or slowness in specific cases. |
| Low | 8 | Polish, hardening and accessibility. |

**Recommendation:** fix all Critical and High items, re-run this test plan, then start uploading content. Note that QA-16 (low raw scores getting no band) also needs a decision from the institution before FLTs are scored.

## Scale test: 1,200 students and 100 staff (3 November 2026)

**Setup:** 1,200 students (half General, half Academic), 90 trainers and 10 admins. A year of history: 60,000 results and 25,000 notifications. 80 FLT slots. The API ran as a separate process with its own PostgreSQL; the browser's automatic retries were simulated. Machine: 16-core laptop, so treat the numbers as a well-resourced single server.

**First run (before the scale fixes):**
- 100 staff opening reports at once crashed the server (out of memory, over 4 GB).
- 919 of 1,200 FLT starts failed with a server error.
- 668 of 1,200 simultaneous sign-ins timed out.
- Trainers saw only 517 of 1,200 pending marksheets.
- The leaderboard read only the newest 10,000 results, so rankings were wrong.

**Fixes:**
- Reports and export aggregate in SQL, with an older-results backfill migration and new indexes; at most 3 reports run at once.
- Transactions wait up to 15 s for a connection (Prisma's default was 2 s), the pool size is configurable (`DATABASE_POOL_SIZE`, default 20), and pool exhaustion returns a retryable 503.
- Sign-in answers "busy" immediately when the queue cannot finish in time, the browser retries with jittered back-off for up to about a minute, and hashing concurrency is configurable (`HASH_CONCURRENCY`).
- Heartbeats no longer read or resend the whole paper: answer keys are cached per attempt (the snapshot is immutable), settings are cached for 5 s, and questions are sent only when the section changes.
- Student dashboards no longer load attempt snapshots; staff dashboards include every pending marksheet and are built at most 6 at once.
- The leaderboard runs in SQL with no row cap.
- Bulk notices are a single insert.
- The listen backlog is 4096.
- Found during this run: two loads of the same exam page could race and lock the student out of saving ("open in another session"). The browser now sends one session key per page load.

**Final run (all scenarios, 0 server errors):**

| Scenario | Result |
|---|---|
| 300 students sign in at the same instant | 300/300, median 9.6 s, slowest 18 s, no retries needed |
| 1,200 students sign in at the same instant | 1,200/1,200 with automatic retries, median 36 s, slowest 71 s |
| 1,200 students start the same FLT | 1,200/1,200, median 5.4 s, slowest 9.1 s |
| 1,200 students save every 3 s for 60 s | 23,172/23,172 saves, 386 per second, median 3.1 s (under the 7.5 s interruption tolerance) |
| 1,200 students submit together | 1,200/1,200, slowest 6.5 s; 1,200 results created |
| 1,200 student dashboards at the same instant | 1,200/1,200, about 11.6 s each |
| 100 staff dashboards at once | 100/100, median 8.7 s, slowest 16 s |
| 100 staff reports at once (60,000 results) | 100/100, median 19.5 s, slowest 38 s (queued 3 at a time) |
| Trainer queue | All 1,200 pending marksheets visible |
| Leaderboard, 300 at once | Median 1.4 s, ranks from all 28,800 eligible results |
| FLT unlock notice (600 students) / announcement (1,200) / bulk release (600) | 21 ms / 150 ms / 3.0 s |
| API memory | Peak about 1.3 GB |

**Limits and requirements:**
1. **Server size.** The API needs at least 2 vCPU and 2 GB RAM, and PostgreSQL at least 2 GB with 50+ connections. The free Render plans (512 MB, 30-day database) cannot run this institution.
2. **One API process is at its limit with 1,200 students in the same timed sitting.** Saves reached 386/s against about 400/s needed. Run 2 API instances for full-cohort sittings, or schedule sittings in batches of up to about 600.
3. **Whole-cohort sign-in at one instant** takes up to about a minute. Sessions last 12 hours, so ask students to sign in before the start time. On larger servers, set `HASH_CONCURRENCY` (with `UV_THREADPOOL_SIZE`) higher.
4. **Staff list pages** load 500 students/results per page with "Load more", and dashboard responses are 1.6–2.2 MB. Server-side search and pagination per page (Students, Results, Evaluation queue) is the recommended next step.
5. **CSV export** is limited to 50,000 rows. With a year of data, "export everything" needs a course or date filter.

## 2. Regressions found in my own earlier commit (fixed locally, not yet pushed)

The baseline run caught three failures in the live end-to-end tests. All were caused by commit `92d2269` (sidebar groups and test builder), which is already on `main`. Because CI runs these tests, **CI on `main` is failing and Render will not deploy that commit** until the fix is pushed. Production is still running the previous version.

| Regression | Fix (uncommitted) |
|---|---|
| Sidebar links put the count into their accessible name ("Students (6)"). Screen readers announced it as part of the name, and tests could not find "Students". | The count is now visual only (`aria-hidden`), so the name stays "Students". |
| The builder's "Apply draft" button was renamed "Save structure" and disabled when nothing had changed. | The button stays enabled, and the live test now uses the new name. |
| Sidebar group IDs were duplicated because the sidebar renders twice (desktop and mobile), which breaks `aria-controls`. | Each instance now gets a unique ID (`useId`). |

After these fixes: demo E2E 18/18, live E2E 15/15 on three consecutive runs, and typecheck and lint are clean. One earlier live run failed 4 tests (see QA-18).

## 4. Findings

### Critical

#### QA-01. A student can freeze the FLT timer indefinitely
**Confirmed.** After a 1-hour gap, the time remaining was unchanged (8,993 s before and after), and the attempt recorded only one interruption.
- The server deducts nothing for any gap longer than 7.5 s between heartbeats ([attempts.ts:69-73](../backend/src/attempts.ts#L69-L73)).
- The browser stops sending heartbeats whenever the tab is hidden ([LiveExam.tsx:19](../frontend/src/pages/student/LiveExam.tsx#L19), [LiveExam.tsx:40](../frontend/src/pages/student/LiveExam.tsx#L40)), so switching tabs is enough. No network tricks are needed.
- Flagging starts only after more than 3 gaps, and a flag has no consequence.

**Fix:**
- Keep sending heartbeats (and counting time) while the tab is hidden.
- Record hidden-tab periods in the attempt log as evidence for review.
- Get a client decision on a maximum wall-clock time per FLT, with auto-submit or forced review when it is exceeded.

#### QA-02. The entire FLT is sent to the browser at the start
**Confirmed.** The start response contains all 82 questions, including the Writing prompts ([views.ts:15](../backend/src/views.ts#L15)). Combined with QA-01 and QA-03, a student can read the whole paper, leave, prepare, and come back with no time lost.

**Fix:** return only the active section's questions, both on start and on resume. Return later sections only once they open.

### High

#### QA-03. FLT sections are not in order
**Confirmed in code and by test.** The server accepts any section number in a heartbeat ([attempts.ts:100-101](../backend/src/attempts.ts#L100-L101)), and the exam tabs allow switching freely. A student can open Writing during Listening time and then go back. Real IELTS runs Listening → Reading → Writing.

**Fix (decision needed):** only allow moving forward to the next section, after the current one is submitted or its time runs out.

#### QA-04. Logins fail when a class signs in together
**Confirmed:** 22 of 40 simultaneous logins got 503 "Sign-in is busy". Password hashing runs 2 jobs at a time with a queue of 16 ([auth.ts:9-16](../backend/src/auth.ts#L9-L16)). That limit protects the 512 MB server, but a class of 30 at exam start will see failures.

**Fix:**
- Let requests queue longer (or wait, rather than rejecting).
- Have the login page retry automatically after a short delay on 503.
- Size the server for the expected class size.

#### QA-05. Starting tests fails when everyone starts at once
**Confirmed:** with 150 students starting the same FLT together, 36 (24%) got 409 "This record changed during saving". The median start took 2.6 s and the 95th percentile 3.6 s. Each start runs a serializable transaction that counts attempts and inserts a large snapshot, so they conflict and run out of the 6 retries in [db.ts:22-30](../backend/src/db.ts#L22-L30). The same conflict errors appeared in the server log during the live E2E runs (QA-18).

**Fix:**
- Starts already lock the student row, so they can run at a lower isolation level (Read Committed with the row lock).
- Build the snapshot once per test version instead of per student.
- Have the client retry a 409 on start automatically.

#### QA-06. Anyone can lock any account out for 15 minutes
**Confirmed:** after 12 wrong passwords, the correct password returns 429. The per-account counter increases before the password is checked, including on successful logins ([app.ts:89-90](../backend/src/app.ts#L89-L90)). Assigned IDs are easy to guess, so someone could lock a classmate out just before an FLT.

**Fix:**
- Before checking the password, only read the failure count.
- Increase it only on a failed login, and reset it on success.
- Prefer progressive delays to a hard block.

#### QA-07. Unlimited paid AI evaluations from blank Writing practice
**Confirmed:** 15 instant blank Writing practice submissions queued 15 AI jobs. The only limit is the general throttle of about 300 writes per minute per student, so one student could trigger thousands of paid calls per hour once an OpenAI key is configured.

**Fix:**
- Skip AI for empty or very short answers.
- Set a per-student daily AI quota (for example 5 per day) and a global daily budget.
- Show Admin the AI usage.

#### QA-08. Practice Mock answer keys appear before the second attempt
**Confirmed:** after attempt 1 is scored, the result page shows every answer. Attempt 2 is the same paper, and the leaderboard and reports count the latest attempt ([app.ts:126](../backend/src/app.ts#L126)).

**Fix (decision needed):** hide keys until both attempts are used, or until the student gives up the second one. Alternatively, rank by the first attempt.

#### QA-09. Abandoned or expired attempts are never closed
**Confirmed:** when access expires during an FLT, heartbeat and submit return 403, and nothing ever closes the attempt. Six attempts were left stuck after the run. The student's only FLT attempt is used up but never produces a result, and Admin has no way to close it.

**Fix:**
- Give Admin an audited "force submit" that scores the saved answers.
- Have the maintenance job close attempts past the wall-clock limit from QA-01.

## 5. Verified working (no issue found)

- **Authorization:** all 25 protected routes rejected every unauthorized role. No 5xx errors from any role.
- **Accounts:** role mismatch and missing Origin are rejected. Disabled, expired and not-yet-active students are blocked. Expired students can read only their own profile status.
- **CSRF:** a missing token, another session's token and a foreign origin are all rejected.
- **Sessions:** revoked on Admin password reset, account disable and logout.
- **Production cookie:** `HttpOnly; Secure; SameSite=Strict`, 12 hours. Full Helmet header set including CSP and HSTS. SPA fallback and API 404s work. Path traversal returns nothing.
- **Login timing:** known and unknown accounts take the same time (about 160–176 ms), so IDs can't be discovered by timing.
- **Data isolation:**
  - another student's attempts, results and notifications are unreachable
  - General and Academic are fully separated
  - unavailable or unpublished FLTs cannot start
  - Speaking content is unreachable
- **Release rules:**
  - an unreleased FLT is hidden on direct URL, bootstrap and leaderboard
  - Trainers cannot release results
  - releasing with Speaking pending works
  - the 3-skill overall for 9 / 9 / 6.5 is 8.0, which is correct
- **Answer keys:** none in the student bootstrap, start or resume payloads. FLT keys are no longer reachable through practice (C1 fix confirmed).
- **Trainer privacy:** no contact details in Trainer bootstrap, reports, filtered reports, CSV export or result views.
- **Races:**
  - 20 parallel FLT starts create exactly 1 attempt
  - 1 of 10 conflicting heartbeats is accepted
  - 8 parallel submits give 1 result
  - the Practice Mock limit holds at 2
  - 1 of 3 concurrent evaluations is saved
  - 6 parallel releases send 1 notification
- **Exam rules:**
  - an expired timer auto-submits and scores
  - the 4th interruption flags the attempt (limit 3)
  - stale sequence replays are rejected
  - answers for questions outside the attempt are rejected
- **Scoring:**
  - all 7 overall and 6 Speaking rounding cases match the PRD rule (.25 → half band, .75 → next whole band)
  - non-half-band scores, fractional Speaking criteria and changes without remarks are rejected
  - score history and the audit log cannot be changed even directly in the database
- **Robustness:**
  - 178 fuzzed requests: no crashes except QA-11 and QA-12
  - a 2 MB body returns 413
  - `__proto__` keys are rejected and no prototype pollution occurred
- **Imports:** random or renamed XLSX, `__proto__` headers, 1001 rows, a 6 MB file, an empty file, formula cells and unknown import types are all rejected with clear messages.
- **Media:** HTML disguised as PNG, SVG, PNG header with HTML, 25 MB and empty files are all rejected. Assets not attached to a student's content are hidden.
- **Load (150 students):**
  - heartbeats: median 9 ms, 99th percentile 26 ms, zero errors across 1,135 requests
  - simultaneous submit: median 0.7 s, zero errors
  - dashboard: median 0.6 s, zero errors
  - with 6,000 results, Admin dashboard 51 ms, Trainer dashboard 35 ms, leaderboard 56 ms
- **Frontend:** 216 page loads across 36 pages and 6 widths:
  - no sideways scrolling, nothing off-screen
  - no console or page errors, no failed API calls
  - every field labelled, every image has alt text
  - keyboard focus visible on the first 25 controls of each dashboard
- **Repository:** no secrets in any of the 27 commits, no tracked `.env` or key files, no private content packs in history.
- **Dependencies:** frontend has 0 vulnerabilities. Backend has a moderate `glob` advisory through `@fastify/static`/`exceljs`; it isn't reachable with untrusted input.
